# Lean work-package execution

Read the project AGENTS.md, current state, governing architecture/public contract, selected package card and relevant mathematical source. Do not load the full historical research archive by default. If no package is selected, the integration lead may choose a ready package within the authorized plan; a worker asks its lead. Do not silently choose a different theorem.

Before editing, resolve owned files, required upstream declarations, source controls, exact acceptance statement or explicit spike deliverable, and the package's integration owner. Check the actual Lean/toolchain/dependency revisions and dirty state. A package can be a measured API spike or integration test; do not invent a nominal theorem to fit a template.

Search exact local declarations and callers before proving replacements. Distinguish public APIs, private proof templates, a general theorem needing an adapter, and unproved mathematical gaps. Prefer a small compiled consumer over an inventory of plausible theorem names. Preserve a rejected candidate and its exact failure when it eliminates meaningful work.

Freeze the mathematical contract before substantial proving. The lead may correct syntax, split helpers, or update dependencies based on compiler evidence without changing that contract. Added public assumptions, weakened conclusions, a different mathematical route with new obligations, or a changed trust boundary require review. Do not ask the operator about routine casts or namespace repairs.

Prototype the difficult representation seam early, alongside independent useful branches. A proof of scalar algebra alone is not evidence that measure, regularity or singular-boundary interfaces are paid. State upstream assumptions explicitly in named conditional theorems; keep them outside the release root. Never create project axioms, placeholder bodies or hidden assumption instances.

Ordinary hypotheses of a genuine reusable theorem are not unresolved proof oracles. For example, a proved generic averaging theorem may assume a Peano expansion; its Gaussian consumer must then prove that expansion. Keep only provisional assemblies with unpaid project-specific inputs outside the release root, not every useful theorem with hypotheses.

Use compiler/LSP goals and diagnostics; do not infer success from a script's existence. Compile incrementally and install upstream Lake targets before compiling consumers. Prefer stable named lemmas over broad automation and unmeasured heartbeat increases. Use the actual joint law before deriving moment consequences.

At package acceptance, record the exact printed theorem and remaining hypotheses, source/port provenance, fresh commands and exits, transitive axiom report, and review result. Allowed axioms are a project policy set: using fewer allowed axioms is not a failure unless a separate exact-footprint regression expectation is intentional. Source scans complement but do not replace transitive checking and statement review.

One owner integrates shared definitions, production imports and Git. Workers own disjoint files and return evidence, not autonomous commits. Coordinate definition changes with every coupled consumer; avoid duplicate definitions that merely have similar notation.

Continue meaningful authorized work. If stuck, preserve the exact goal, minimal reproducer, declarations tried and smallest missing interface. Do not treat a finished leaf or unchanging arbitrary calendar as the project stop condition. Follow the project's resource and authority boundaries; the skill creates no new permission.

Before declaring the project complete, require all public assumptions discharged, current warning-clean builds, independent statement fidelity review, a fresh coverage-checked axiom audit and clean-checkout reproduction under exact pins. Cached builds, historical logs and conditional assemblies retain their narrower labels.
